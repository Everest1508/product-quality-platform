## 1. Office hours and lateness

### The rule

10:00–19:00 with a 60-minute unpaid break — 8 working hours a day. Arriving late
costs money, in three bands:

| Arrival | Lateness | Outcome |
| --- | --- | --- |
| up to 10:15 | within grace | on time, nothing deducted |
| 10:15 – 10:30 | up to 30 min | **Rs 50** |
| 10:30 – 11:00 | up to 60 min | **Rs 100** |
| after 11:00 | over 60 min | **half a day's pay** |

Bands are **inclusive at the top**: 10:30 exactly is still Rs 50, 11:00 exactly is
still Rs 100, and 11:01 is the half day. This reading of the policy was a
judgement call — the boundaries were described as ranges, and a shared endpoint
belongs to one of them — so it is the first thing to check if the deduction looks
wrong. The bands are stored as *minutes after `start_time`* rather than as clock
times, so the whole thing is one number to reason about and moving the start time
moves the bands with it. Verified against `band_for_late_minutes`:

| Minutes late | 15 | 16 | 30 | 31 | 60 | 61 |
| --- | --- | --- | --- | --- | --- | --- |
| Band | on time | minor | minor | major | major | half day |

### `WorkShift` — one row per company

These numbers live in a model rather than in code because every late penalty and
every "hours worked" figure is derived from them. One row per company
(`get_or_create` in `shift_for`); the defaults are the office policy above.

### Hours are shown net of the break

The 60-minute break is subtracted only from a day long enough to contain it, so a
full 10:00–19:00 day reads **8h** instead of 9h, while a genuinely short day is
not under-reported. This was wrong before: hours were the raw span, so a normal
full day showed 9h.

### Penalties are derived, never stored

There is deliberately **no `LatePenalty` model**. The penalty is a function of
`(shift, punch-in time)` — recomputing it from the shift would be wrong if the
company's hours changed after the fact, and storing it would create a second
source of truth to keep in step with payroll. What *is* snapshotted onto the
payslip is the money, so a historical slip cannot silently change when someone
edits the shift.

## 2. Lateness in payroll

`preview()` and `generate_run()` share the calculation, so the estimate an admin
sees and the issued run can never disagree. The payslip carries `late_penalty`
and `late_half_days`, and **every event** behind them — date, check-in time,
lateness in minutes, which band, and the cost — is rendered on both the admin
payslip and the employee's own.

A half day reduces payable days at half the daily rate, exactly like unpaid
leave. That keeps the arithmetic legible: gross is always `payable_days × rate`,
and the late charge is a separate line that reduces what is paid.

## 3. Leave

Leave became admin-configurable rather than hard-coded:

- **Allowance is 17 days** — 12 casual + 5 sick — and the cap is now **three
  working days across all leave types combined** rather than per policy. The
  cap is checked on the *combined run*: 2 casual days followed by 2 sick days is
  four days away, and the office rule caps the run, not the type. Counted in
  working days, so Friday + Monday is 2, not 4.
- Unpaid leave has no year limit and no spell cap, because neither applies to it.
- The seeded "Medical" policy is renamed **Sick** everywhere — three places still
  said "medical" after the earlier rename.
- Leave types carry a **colour and an icon**, both from closed allowlists: colour
  resolves to a CSS class and icon to a template lookup, so neither can be used to
  inject markup. "Paid" is now a labelled switch rather than a bare checkbox.
- `/leave/policies/` was reduced to one heading and one labelled row per type.
  Dropped: the breadcrumb, a subtitle, a duplicate card header, the usage
  columns, and "Unlimited" — a blank limit now reads `No cap`, because 0 is a real
  setting and conflating it with "no limit" would be a lie.

## 4. Sidebar

### Nav coverage

Two features were reachable only by typing a URL. "All automation" and "All
feedback" are now global nav items.

Active state matches **resolved URL names** instead of substring-matching path
names. Before, seven pages highlighted nothing: `/leave/apply/` matched a route
name that does not exist, `/automation/`, `/automation/create/`, `/feedback/` and
`/feedback/create/` had no nav entry at all, `/payroll/holidays/` was a tab
Payroll did not claim, and `/profile/` now marks the user-menu link. The
invariant is exactly one `aria-current="page"` per page, and the full list is
pinned by a test.

The four `<nav>` landmarks now have named `aria-label`s (Main / Current product /
Operations / Admin), so a screen reader no longer announces four identical
"navigation" entries.

### The blank page: one surplus `</div>`

**The entire page to the right of the sidebar rendered blank white.** A stray
`</div>` in `_sidebar.html` closed the `<aside>` early, so `<div class="main">`
was parsed *inside* it. `.shell` is a two-column grid, so the fixed-width sidebar
then clipped the whole application.

The instructive part is how little evidence there was: no view error, no CSS
change, no stale cache. The HTML itself was malformed, so every tool that reports
"did the view raise?" said the page was fine.
`test_the_main_column_is_not_swallowed_by_the_sidebar` now asserts that every tag
balances *and* that `.main` is a sibling of the sidebar, and was confirmed to fail
when the stray `</div>` is reintroduced.

### Two CSS bugs, both from one declaration

The active-sidebar indicator disappeared whenever the sidebar was collapsed, and
the collapsed hover tooltip never appeared at all. Both were being clipped by
`overflow:hidden` on the item that positioned them *outside its own box*. The
ellipsis now lives on the label, where it belongs. Section dividers also draw in
both sidebar states instead of the collapsed state only.

A styled tooltip and a native one fired together on every nav link (`data-label`
and `title` were both set); `data-label` is now the only source.

## 5. Fixed along the way

Things that were quietly wrong rather than missing:

- The employee payslip stated *"Unpaid leave is the only thing that reduces it"* —
  untrue as soon as lateness could.
- **The seed was time-of-day dependent.** Demo punch times for "today" were
  `now - N hours`, so seeded data changed with the hour the command ran, and past
  10:15 it manufactured a *real* late penalty out of demo data — which surfaced
  as a payroll test that passed at 09:00 and failed at 14:25. Arrival times are
  now derived from the shift start, with a fallback if the command runs before the
  shift.
- The test that caught it asserted `gross == payable_days × daily_rate` as a
  blanket rule, which encoded a world where nothing could deduct cash. It now
  subtracts `late_penalty`.

## 6. Found by sweeping, not by looking

After the blank-page fix I crawled every GET-able route as all four roles —
**330 page/role combinations** — checking each rendered page for HTTP errors and
for HTML that does not balance. Two more defects turned up, neither of which I was
looking at:

- **`/products/create` was malformed in exactly the same way as the sidebar.** The
  Notifications `.form-section` was never closed, so Milestones nested inside it
  and `</form>` matched nothing. Pre-existing, not from today, and on a page every
  owner visits.
- **Negative gross payslips.** `payable_days` was floored at zero, but the cash
  charge was applied *after* that floor, so on a low salary, being Rs 100 late
  every day of the cycle cost more than the month and the slip came out at
  **-99.96**. Payroll does not issue negative pay, so the charge is now capped at
  what the payable days can absorb and gross floors at zero. The uncapped figure
  stays in `breakdown["late_penalty_uncapped"]` — capping silently would be the
  same class of move as the seed that hid a real penalty, just in the other
  direction. Ordinary payslips are untouched: the cap only engages when the
  charge exceeds the whole month's pay.
- **`/attendance/history/` was dead code.** It returned a bare `<table>` fragment
  with no page shell, nothing linked to it, and no `hx-get` loaded it — the
  partial is already included server-side in `my_attendance.html`. Removed the
  route, the view, its test, and the stale `history` in the sidebar condition.

The crawl is worth repeating rather than trusting once: it is the only reason the
product-form bug surfaced at all.

## 7. Labels: the same bug, 90 times

Balanced HTML is not the same as *usable* HTML, so the same crawl was then run
through an accessibility pass: every rendered `<input>`, `<select>` and
`<textarea>` checked for an associated `<label for>` or an `aria-label`, plus
duplicate `id`s, nameless buttons, and `target="_blank"` without
`rel="noopener"`. Across 28 pages it found **87 unlabelled controls, 6 external
links with no `rel="noopener"`, and 8 duplicated ids**. Three more unlabelled
controls surfaced on a later re-run — see the end of this section, because the
reason is the point. Everything is now zero except one deliberate exception.

The dominant pattern, and the reason it was so widespread, is structural:

```html
<label class="form-section-label">Rule Name</label>
<input type="text" name="name" class="form-input">
```

A sibling `<label>` with no `for` is associated with **nothing**. Clicking
"Rule Name" does not focus the field, and a screen reader announces an unlabelled
text field — the visible text next to a control looks like a label to every
sighted user and is invisible to assistive tech. The same file gets it right one
line later by *wrapping* the checkbox, which is why the inconsistency was
invisible when reading the template.

| Count | Defect | Fix |
| --- | --- | --- |
| 45 | `input.ticket-select`, the bulk-select box on every ticket card, with no accessible name | `aria-label="Select ticket {{ pk }}"` |
| 12 | search and filter/sort `<select>`s relying on `placeholder` alone | real `aria-label` derived from the placeholder |
| 6 | `target="_blank"` with no `rel="noopener"` on the CS Hub link | `rel="noopener noreferrer"` |
| 3 | `id_is_on_payroll` / `id_effective_from` repeated on every payroll row | per-member ids, matching the existing `id_currency_{pk}` |

The 45 ticket checkboxes are one template line, which is the argument for auditing
by rendered output rather than by reading templates: no amount of reading finds
45 instances of anything.

### The sweep was not finished by the first pass

Re-running the same audit later — with a real HTML parser instead of a regex, and
skipping controls the page's own CSS hides — turned up **three more controls**
that the first pass had missed, and it is worth being precise about why:

- The audit-log filter row had `aria-label="Filter by type"` on one `<select>`
  and nothing on the `<select>` for member beside it. Same template, same row,
  one line apart.
- The two date inputs were introduced by `<span>From</span>` and
  `<span>To</span>`. A span is not a label at all, so clicking "From" did not
  focus the field. They are `<label for="audit-from">` now.
- The assignees picker hides its native `<select>` with `display:none` and stands
  up a `<div role="button">` in its place. That div is what assistive tech
  actually meets, and it had no accessible name, no `aria-haspopup` and no
  `aria-expanded` — and its per-assignee "remove" chip said *Remove assignee*
  for everyone, which is three identical buttons announcing the same action. The
  chip now says `Remove <name>`.

The lesson is the same one as the blank sidebar: **the first sweep's clean result
was partly an artefact of the tool, not the templates.** An unlabelled control
behind a `display:none` rule, or a `<span>` standing in for a `<label>`, is not
something a "does every input have a label?" grep finds, because in the DOM the
visible text looks like a label to anyone reading the source.

**The DSR sheet was the one real duplicate-id bug, and it was self-inflicted.**
Its add form renders twice — once in the bar above the table and once in the
table's empty state — from one form instance, so every field id appeared twice.
Fixed by giving `DSREntryForm` an `id_prefix` that stamps widget ids and
instantiating it twice, with the template using `{{ field.id_for_label }}`. Two
things are worth recording:

- The id cannot be fixed from a template. `{{ f.as_widget(attrs={"id": …}) }}` is
  a **syntax error** in Django's template language — method arguments are not
  supported — so the first attempt broke all 22 DSR tests. The prefix has to live
  on the form. `{{ field.id_for_label }}` then keeps label and input in sync
  automatically.
- `test_add_form_ids_are_unique_across_both_copies` now pins this, and was
  confirmed to fail when the prefix is removed.

One case is left deliberately: Django renders a hidden
`<input name="initial-effective_from" id="initial-id_effective_from">` per row,
because `show_hidden_initial` builds a *fresh* `HiddenInput` that widget `attrs`
never reach. Turning it off would change payroll save semantics to fix an `id` on
a control that nothing can reference or focus, so it is left alone.

## 8. Version and changelog in the UI

The version is now visible in the sidebar footer and clickable.

```
✨  What's new          v1.0.0
```

- **Two API endpoints.** `GET /api/v1/version/` returns the running version;
  `GET /api/v1/changelog/` returns it plus `CHANGELOG.md` parsed into releases,
  sections and items.
- **The changelog is fetched, the version is not.** The label is rendered by the
  template so it is visible on first paint with no layout shift; the dialog
  content comes from the API because it is tens of kilobytes that nobody scrolls
  past.
- **`APP_VERSION = "1.0.0"`** in settings, overridable with `DJANGO_APP_VERSION`.
  There are no git tags in this repo, so `git describe` yields only a commit hash,
  which is not something to show a user.
- **`apps.core.changelog` parses the file** rather than rendering Markdown in the
  template — a deliberately small parser for the subset the file actually uses,
  memoised against the file's mtime so a request is a `stat()` rather than a
  re-parse. Text is HTML-escaped **before** the inline `**bold**`, `` `code` ``
  and `[text](url)` markers are re-introduced, so formatting can never emit markup
  that came from the file, and link targets are restricted to http/https and
  site-relative paths.
- **Both endpoints require a logged-in session, deliberately.** `/api/v1/` also
  serves the public ingestion API, and this changelog carries a `Security`
  section naming a leaked-credential bug — serving that anonymously would publish
  the attack surface. Anonymous callers get 403.
- The dialog lives outside `.shell` because `.sidebar` is `overflow-x:hidden` and
  would clip it, and the trigger dispatches a `pq:changelog` window event since
  the two are in different files. Focus moves to the close button on open and back
  to the trigger on close.

### What the reader actually gets

A changelog exists to answer *what changed in the version I'm looking at*, and the
first version of this dialog did not. It rendered the entire file: **55 bullets
across three blocks, in one scroll**, under three headings that all read
"Unreleased", two of them carrying the same date. That is a wall, and a wall
answers nothing. Worse, the first *item* in the list was a single **2,602-character
paragraph**: `CHANGELOG.md` writes detail as indented sub-bullets under a bolded
lead-in, and the parser was flattening them into the parent with literal `-`
separators between them.

It now opens on the newest release alone — **23 items**, under a header reading
*23 changes in this version · 30 Sep 2026* — with:

- **Sub-bullets rendered as a real nested list.** The 2,602-character item is now
  a one-sentence lead-in plus its sub-points. The parser recognises one level of
  indentation, and the longest remaining lead-in in the newest release is 236
  characters, down from 1,072.
- **Type chips** (All 23 · New 8 · Improved 4 · Fixed 10 · Security 1), so "what
  got fixed?" is one click instead of twenty scrolls. They carry their counts, so
  a reader can see whether a click is worth making, and they use `aria-pressed`.
- **Older releases behind `Show 2 earlier updates`**, a disclosure with
  `aria-expanded` and `aria-controls`. Reachable, not in the way.
- **Plain-English section names.** The `###` headings in the file are written for
  whoever maintains it, and they are diff vocabulary: a user is told something is
  *Added* or *Changed*, which describes the commit rather than the effect. They
  see **New** and **Improved** instead, and *Known issues* instead of *Known
  issues (pre-existing, not addressed here)*.
- **The release title as the heading.** Two blocks here share the tag `Unreleased`
  and the date `2026-09-04`, so the title is the only thing that tells them
  apart; a release with no title falls back to *General updates*. The tag drops to
  a badge, because "Unreleased" three times is noise.
- **Dates as `30 Sep 2026`**, formatted in the one place a date reaches the UI.

The parser now emits what the dialog renders from — a stable `slug` per section,
a `label`, a `count`, `item_count` and `heading` per release — instead of leaving
the client to count and re-label everything. That is also what makes the contract
testable: `test_api_carries_the_fields_the_dialog_renders_from` fails if either
side drifts.

## 9. A committed API token, and two scripts that break the test run

Found while explaining two suite errors that were **not** caused by this work.

`test_api.py` and `test_api10.py` sit in the repository root and have been
committed since `d764ba9` ("fix: ticket creation", 2026-07-29). They are manual
probe scripts, not tests, and two things follow:

1. **Django's discovery matches `test*.py`**, so `manage.py test` imports both.
   `test_api.py:24` calls `req.add_header('Content-Type', None)`, which raises
   `TypeError: expected string or bytes-like object, got 'NoneType'` at *import*
   time. Both surface as `unittest.loader._FailedTest` errors.
2. **`test_api.py:4` contains a live API token in plaintext**, committed to
   version control. It is a `Bearer` credential for `POST /api/v1/tickets/`. It
   does **not** validate against the current development database — the three
   `APIKey` rows there have different prefixes — but if that key was ever valid in
   staging or production, it has been readable by anyone with repo access since
   July and **should be rotated**. The token itself is not repeated here.

There is a second-order problem: because the scripts execute on import, running
the test suite issues **real `POST` requests to whatever server is listening on
`localhost:8000`**. A developer with the dev server up was having their local
database written to by their own test run.

Not changed, because these are committed files and the token needs rotating
rather than editing in place — but the fix is small: move them under `scripts/`
or rename to `probe_api.py` so discovery skips them, delete the hardcoded key,
and read it from the environment.

## 10. Deliberately not built

- **Non-salaried "over 45 minutes late in a week earns half a Saturday."** Not
  implemented and it has no payroll effect, because those staff are not on this
  payroll — `PayrollProfile` has no employment-type field, so the late rules
  apply to everyone it pays. Adding a Saturday-makeup column also needs a prior
  decision: how is a make-up day priced?
- **No `WorkShift` admin screen.** The model exists and is honoured, but the hours
  and bands are only editable in the shell. The company has one set of office
  hours, and a settings screen for a single global value is not obviously worth
  the surface area — flagging it rather than deciding it.
- **No `LatePenalty` model, deliberately** — see §1.
